## Action Schema Draft (v0)
<!-- Common envelope and per-action payloads -->
Base envelope (all actions):
- `type`: one of `communicate`, `decide`, `propose`, `respond`, `transfer`
- `actor_id`: agent identifier string
- `timestamp`: ISO-8601 or integer step index
- `payload`: action-specific object
- `meta`: optional object (e.g., `trace_id`, `turn_id`, `model_version`)

`communicate` payload:
- `channel`: `broadcast` | `direct`
- `recipients`: list of agent ids (required for `direct`)
- `content`: string
- `content_type`: `text` | `json`

`decide` payload:
- `decision_id`: string (scoped to task)
- `choice`: string | number | object
- `reveal`: `sequential` | `aggregated` | `simultaneous`

`propose` payload:
- `proposal_id`: string
- `target_ids`: list of agent ids
- `terms`: object (task-defined structure)
- `expires_at`: optional timestamp or step

`respond` payload:
- `proposal_id`: string
- `response`: `accept` | `reject` | `counter`
- `counter_terms`: object (required if `counter`)

`transfer` payload:
- `resource_id`: string
- `amount`: number
- `to`: agent id

Validation notes:
- Required fields must be present and non-empty.
- `respond.counter` requires `counter_terms`.
- `communicate.direct` requires non-empty `recipients`.
- `transfer.amount` must be positive.

## Agent Interface Contract (v0)
<!-- Inputs, outputs, metadata, and lifecycle hooks -->
Required metadata:
- `agent_id`: string (unique)
- `role`: string
- `model`: `{ provider, name, version?, temperature?, top_p?, max_tokens? }`
- `prompt_version`: string

Observation input:
- `state`: partial state snapshot (only visible fields)
- `visible_events`: list of recent events visible to agent
- `memory`: optional agent-specific memory snapshot
- `step_index`: integer

Action proposal output:
- `action`: single action payload (must match action schema)
- `rationale`: optional string (for research logging only)
- `alternatives`: optional ranked list of actions

Lifecycle hooks:
- `reset(seed)`: clear internal state for reproducibility
- `serialize()`: return JSON-serializable internal state
- `load(state)`: restore internal state

## Event Taxonomy & Trace Schema (v0)
<!-- Deterministic event logging for replay and metrics -->
Base event envelope:
- `event_id`: unique id
- `event_type`: string enum
- `timestamp`: ISO-8601 or integer step index
- `actor_id`: agent or system id
- `visibility`: `public` | `private` | `system`
- `payload`: event-specific object
- `meta`: optional object (e.g., `trace_id`, `turn_id`, `schema_version`)

Core event types:
- `action_submitted`: raw action received from agent
- `action_validated`: action passed schema + precondition checks
- `action_rejected`: action failed validation with reasons
- `state_updated`: state delta applied (atomic update)
- `message_delivered`: communication delivered to recipients
- `decision_buffered`: decision stored pending reveal
- `decision_revealed`: decision revealed to eligible agents
- `probe_asked`: interviewer question issued
- `probe_answered`: interviewer response recorded

Payload highlights:
- `action_submitted`: `{ action }`
- `action_validated`: `{ action, checks_passed }`
- `action_rejected`: `{ action, error_code, error_message }`
- `state_updated`: `{ state_delta, resulting_state_hash }`
- `message_delivered`: `{ message_id, recipients }`
- `decision_buffered`: `{ decision_id, buffer_size }`
- `decision_revealed`: `{ decision_id, choices }`
- `probe_asked`: `{ probe_id, prompt_version, question }`
- `probe_answered`: `{ probe_id, response, confidence? }`

Ordering guarantees:
- Events are total-ordered by `(timestamp, event_id)`.
- For a single action, events must appear in order:
  `action_submitted` -> (`action_validated` | `action_rejected`) -> `state_updated` (if validated).
Visibility rules:
- `public`: visible to all agents.
- `private`: visible only to specified recipients.
- `system`: only in logs (not delivered to agents).

## Controller Loop & State Model (v0)
<!-- Deterministic execution model -->
State components:
- `agents`: registry with roles and resource holdings
- `task_state`: task-specific variables and objectives
- `resources`: global resource ledger
- `turn_state`: current turn, active agent(s), phase
- `buffers`: decision buffers for `simultaneous`/`aggregated` reveals
- `visibility_map`: who can observe which state fields
- `history`: event log reference + state hash

Controller loop (per step):
1. Build `observation` for active agent(s) using `visibility_map`.
2. Request agent action proposal(s).
3. Emit `action_submitted` event(s).
4. Validate schema + preconditions (turn order, resources, timing).
5. If invalid: emit `action_rejected` and continue.
6. If valid: emit `action_validated` and apply atomic state update.
7. Emit `state_updated` + any derived events (message delivery, decision buffering).
8. If decision reveal condition met, emit `decision_revealed`.
9. Trigger interviewer probe for configured events, emit `probe_asked/answered`.
10. Check termination conditions; if met, finalize run.

Buffering logic:
- `simultaneous`: store all choices until all eligible agents submit.
- `aggregated`: store choices, reveal when quorum/timeout met.
- `sequential`: reveal immediately in turn order.

Termination conditions:
- `max_steps`, `task_complete`, `timeout`, or custom task-defined condition.

## Metrics Computation Pipeline (v0)
<!-- From traces + probes to metrics -->
Inputs:
- `event_log`: ordered events per run
- `probe_log`: probe questions and responses
- `task_outcome`: completion status and scores (task-specific)

Stages:
1. Extract: parse events into action timelines and interaction graphs
2. Align: join probe responses to action timestamps and actors
3. Compute: metric formulas per construct
4. Aggregate: per-agent, per-dyad, per-run summaries

Grounding metrics:
- `belief_accuracy`: match `partner_intent` vs partner stated goals
- `clarification_rate`: count clarification messages per 100 actions
- `communication_overhead`: coordination vs task message ratio

Situation awareness metrics:
- `partner_model_accuracy`: match `predicted_action` vs actual next action
- `info_distribution_awareness`: correct attribution of who knows what
- `anticipatory_coordination`: actions addressing predicted partner needs

Coordination metrics:
- `synchronization_efficiency`: latency between interdependent actions
- `adaptation_latency`: time to adjust after partner change
- `conflict_resolution_success`: fraction of resolved breakdowns

Outputs:
- `metrics_per_agent`: dict of metric values
- `metrics_per_run`: aggregated run-level values
- `metrics_summary`: cross-run means/CI

## Metrics Validation Plan (v0)
<!-- Synthetic + adversarial trace scenarios -->
Synthetic trace templates:
- Grounding-high: correct `partner_intent` probes, low clarification rate
- Grounding-low: incorrect intent probes, high clarification rate
- Situation awareness-high: correct `predicted_action` alignment
- Situation awareness-low: incorrect predictions and missed info attribution
- Coordination-high: low latency interdependent actions, resolved conflicts
- Coordination-low: delayed responses, unresolved breakdowns

Adversarial traces:
- Conflicting probes: correct behavior but incorrect stated beliefs
- Sparse communication: minimal messages with high task success
- Message spam: high coordination messages with low task progress

Acceptance criteria:
- Metrics monotonicity: high > low for each construct
- Sensitivity: detect directional change under adversarial traces
- Robustness: no metric explosion under sparse/spam cases
